# Olist 巴西电商运营分析看板

基于 Kaggle Olist 公开数据集（99,441 笔订单 / 2016-09 ~ 2018-10）的端到端 BI 项目：
原始数据清洗 → 星型模型建模 → 指标体系设计 → Power BI 六页看板 + 离线 HTML 看板，
并用 **SQL 独立复刻**全部指标做交叉验证。

三端产出口径完全一致：Power BI 看板（6 页 / 85 个 DAX 度量值）、ECharts 单文件 HTML 看板（离线可开）、DuckDB SQL 脚本（可复跑）。

> **在线交互看板**：https://l1ght1nk.github.io/olist-ecommerce-bi/
> 浏览器直接打开，无需下载、无需安装任何东西。

## 数据流水线

1. `01_explore.py` — 探查 9 张原始表的缺失率、异常值、字段语义
2. `02_clean_model.py` — 清洗并建模为星型结构（2 张事实表 + 6 张维度表）
3. `03_metrics.py` — 计算指标层，作为后续所有口径的基准
4. `05_holiday.py` — 节日效应：基线、节前 7 日、当天、节后 7 日对比
5. `06_build_fact.py` — 压缩成看板用的紧凑事实表
6. 三条分支产出：
   - `04_build_dashboard.py` → ECharts 单文件 HTML 看板
   - Power BI Import + 85 个 DAX 度量值 → 六页交互看板
   - `sql/*.sql`（DuckDB 独立实现）→ 与 pandas 结果对账

复现步骤（原始数据需自行从 Kaggle 下载）：

```bash
pip install pandas duckdb
python 02_clean_model.py        # 生成 output/*.csv
python 04_build_dashboard.py    # 渲染看板 HTML，并同步产出 index.html
python run_sql.py               # SQL 复刻并与 pandas 对账
```

> 数据源：[Brazilian E-Commerce Public Dataset by Olist](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce)

## 数据模型（星型）

| 类型 | 表 | 行数 | 说明 |
|---|---|---|---|
| 事实 | `fact_orders` | 99,441 | 订单级：GMV、配送时效、评分、支付 |
| 事实 | `fact_order_items` | 112,650 | 明细级：商品、卖家、价格、运费 |
| 维度 | `dim_customer` | 96,096 | 以 `customer_unique_id` 作为真实客户（其中 93,358 人有已交付订单） |
| 维度 | `dim_product` | 32,951 | 含葡语 / 英语双品类列 |
| 维度 | `dim_seller` | 3,095 | 卖家 |
| 维度 | `dim_date` | 1,096 | 已标记日期表，含 `is_complete_month` |
| 维度 | `dim_geolocation` | 19,015 | 邮编级地理信息 |
| 维度 | `dim_holiday` | 26 | 巴西节假日（双向筛选） |

Power BI 中另建 5 张静态表（`holiday_uplift` / `bf_weeks` / `bf_day_vs_normal` / `bf_category` / `bf_series`）。
原因是节日基线涉及多重窗口比较，用 DAX 实现性价比低，改为预计算后导入，不建关系、不接切片器。

## 指标体系与口径规则

85 个 DAX 度量值，按 8 个显示文件夹组织：基础运营、履约与评价、客户、时间智能、商品与卖家、节假日大促、卡片时点、卡片展示用。

### 五条口径规则

| # | 规则 | 原因 |
|---|---|---|
| 1 | 客户标识用 `customer_unique_id`，不用 `customer_id` | `customer_id` 是订单级的，同一个人在不同订单下 id 不同。用错则复购率恒等于 0 |
| 2 | GMV = 商品金额 + 运费，且只统计 `is_delivered = TRUE` | 未送达订单（2,963 单 / R$423,779）不应计入业绩 |
| 3 | 趋势分析必须开 `is_complete_month = TRUE` | 2016-09~12 是平台爬坡期（月订单仅 1~324 单），2018-09~10 数据被截断。不开会把爬坡期误读成"业务暴跌"。完整月为 2017-01 ~ 2018-08 共 20 个月 |
| 4 | RFM 的 F 用业务映射，不用等频分位 | 复购率仅 3.00%、96% 客户只有 1 单，等频分位会把绝大多数人挤进同一档。改为 1 单=1 / 2 单=3 / 3 单及以上=5 |
| 5 | 评分类指标保留全量口径 | 平均评分 4.09 / 差评率 11.52% 含未送达订单（均分仅 1.74，其中 70.6% 打 1 星）。没收到货的 1 星同样是口碑，改用 delivered 口径（4.16 / 9.76%）会掩盖履约问题 |

### 踩过的坑

**布尔标记列的 FALSE 会包含"不适用"的记录。**
`is_late = FALSE` 会把 2,963 单未送达订单一起算进来，导致【准时率】虚高到 94.96%（正确 91.89%）、
【准时订单评分】被拉低到 4.21（正确 4.29）。修法是分子必须同时限定 `is_delivered = TRUE`。
自洽校验方法：准时率 + 延误率 必须等于 100%，不等即说明口径有漏。

**帕累托累计占比要用 `ALL()` 而非 `ALLSELECTED()`。**
后者会保留外部筛选，导致每个品类的累计占比都算成 100%。且柱与线必须使用同一个度量值，
否则累计线忽上忽下却不报错。

**品类 / 卖家维度必须拖【明细 GMV】。**
拖【总 GMV】会因为缺少关系路径而静默返回全平台总额，数字看起来"正确"实则失真。

**新版卡片图没有"显示单位"开关**，数字会被自动缩位成「93千」。
解法是建 `FORMAT([度量值], "#,0")` 的文本度量值专供卡片使用。

**MAU / DAU 是时点指标**，卡片上不加月份筛选会退化成全期值。
解法是把 `year_month = "2018-08"` 直接写进 DAX。

## 核心业务结论

**规模与效率**

- GMV R$15,419,774 ｜ 订单 96,478 ｜ 客户 93,358 ｜ AOV R$159.83 ｜ ARPU R$165.17
- 运费 R$2,198,276，占商品金额 16.63%（占 GMV 14.26%），符合巴西地域辽阔、物流基建薄弱的市场特征

**履约是口碑的第一杠杆**

- 交付完成率 97.02% ｜ 准时率 91.89% ｜ 平均配送 12.56 天
- 配送时长与评分严格单调负相关：0-5 天差评率 5.1%，20 天以上升至 29.0%
- 延误订单评分 2.57，准时订单 4.29，相差 1.72 分
- 未送达订单均分仅 1.74，其中 70.6% 直接打 1 星

**增长靠拉新，不靠留存**

- 复购率仅 3.00%（已交付口径；含未送达的全量口径为 2.91%），人均订单 1.033 单，新客订单占比 97.59%
- MAU（2018-08）6,310 ｜ 月均 DAU 218.5 ｜ 用户粘性 3.46%
- 平台本质是一次性流量生意，留存体系缺位，这是最大的增长风险

**供给高度集中**

- TOP10 品类贡献 62.4% GMV，其余 62 个品类分掉 37.6%
- TOP10% 卖家（297 家）贡献 67.11% GMV，头部依赖严重

**大促效应：黑五是唯一的量级级爆发**

- 2017-11-24 当天 1,147 单 / R$175,178，相对基线 +719.3%
- 节前 7 日 +41.0%，节后 7 日仍 +152.8%，说明没有透支消费
- 黑五当天信用卡占比 79.7%（日常 74.3%）、平均分期 3.59 期（日常 2.92），大促显著推高分期需求
- 但 20 个节日里只有 4 个当天为正，圣诞 -60%、元旦 -100%，节日营销普遍失效

## 技术栈

- **Python**：pandas / numpy，负责清洗、建模、指标计算

## 为什么做三端交叉验证

pandas 与 SQL 各自独立实现同一套口径，16 项核心指标对账零差异。
正是这个动作抓出了一个隐蔽 bug：pandas 中 `(~df['is_late']).mean()` 在 `is_late` 为 object dtype 时
退化为按位取反（`~True = -2`），算出 −108% 的荒谬值，且不报任何错。

详见 [README_SQL.md](README_SQL.md)。
